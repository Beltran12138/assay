# 「较真」判分 Rubric（设计底稿 v0）

> 这是产品的**护城河**。研究结论：判"论证质量"必须用**带推理的 judge**，且分歧主因是
> **rubric 未定义**而非模型个性（assay 实证 53%→83%）。所以本 rubric 的价值在于
> **锚点明确 + 谬误闭集 + 强制引用原文 span + 外部锚（知乎权威内容）**——这四条正是
> "为什么我的判分可信"的技术答案，也是对评委"套壳 LLM"质疑的正面回击。
>
> ⚠️ 合规：议题只取**安全域**（学习/职业/科普/生活/产品选型），禁政治/社会争议。

## 输入
- `topic`：一个有争议的问题（如"该不该读研""远程办公是不是更高效""新手该学 Rust 还是 Go"）
- `arena`：知乎搜索拉来的正反方**高权威（AuthorityLevel≥3）高赞**回答 + 精选评论（含反驳）
- `user_argument`：用户写的一段论证/立场

## 四维评分（每维 0-3，总分 0-12）——每维必须"先判据后给分"

### 维度 1 · 主张 Claim
| 分 | 锚点 |
|---|---|
| 0 | 无明确主张，或自相矛盾 |
| 1 | 有主张但模糊 / 混了多个未拆分的主张 |
| 2 | 单一、清晰的主张 |
| 3 | 清晰主张 **+ 明确限定条件**（适用范围 / 前提） |

### 维度 2 · 证据 Evidence
| 分 | 锚点 |
|---|---|
| 0 | 纯断言，无任何证据 |
| 1 | 有证据但与主张弱相关 / 来源不可核 |
| 2 | 相关且可核的证据支撑主张 |
| 3 | 多类证据（数据 / 案例 / 机制）+ **说明证据如何支撑主张** |

### 维度 3 · 逻辑 Logic（谬误检测，闭集）
| 分 | 锚点 |
|---|---|
| 0 | 存在**致命谬误**（下列清单），结论不成立 |
| 1 | 有谬误但不致命 |
| 2 | 推理基本有效，无明显谬误 |
| 3 | 推理链完整，前提→结论无跳步 |

**谬误闭集**（judge 只能从此集判定，不许自创，保证稳定可复现）：
`滑坡` `稻草人` `诉诸情感` `诉诸权威` `以偏概全` `循环论证` `虚假两难` `偷换概念` `因果倒置`

### 维度 4 · 反方处理 Steelman
| 分 | 锚点 |
|---|---|
| 0 | 无视反方 / 只打稻草人 |
| 1 | 提到反方但轻描淡写 |
| 2 | 正面回应了一个**真实**反方论点 |
| 3 | 回应了 `arena` 里知乎高赞的**最强**反方（steelman）并给出反驳 |

## 输出（结构化 JSON，强制可核）
```json
{
  "scores": { "claim": 2, "evidence": 1, "logic": 0, "steelman": 1 },
  "total": 4,
  "findings": [
    {
      "dim": "logic",
      "verdict": "滑坡",
      "span": "用户原文里被判定的那句（逐字引用）",
      "why": "从『偶尔加班』直接推到『必然过劳死』，中间缺环节",
      "fix": "补上中间因果，或弱化结论强度"
    }
  ],
  "vs_zhihu": {
    "strongest_counter": "arena 中最强反方论点（引用来源 Url）",
    "you_missed": "用户没有回应的那个反方点"
  }
}
```

## 判分引擎设计要点（写进计划书"技术亮点"）
1. **reasoning judge**：用带推理的模型（自带 Claude/GLM reasoning，或 `zhida-thinking-1p5`），每维**先输出判据再给分**（研究：explicit reasoning → better judge）。
2. **强制引用 span**：每个 finding 必须逐字引用用户原文被判定的片段——判定可核，不是黑箱。
3. **谬误闭集**：只在 9 类里判，消除"模型瞎发明谬误名"的不稳定。
4. **外部锚**：`vs_zhihu` 用知乎**权威度分级**内容当准 ground-truth、用**精选评论**当现成反方——这是别处"裸调 LLM"没有的锚，也是"知乎生态契合度"的实证。
5. **可信度自证（可选加分）**：同一论证判两次看一致性（重测信度），一致率低的维度标"低置信"——把 assay 的方法论直接搬来当卖点。
